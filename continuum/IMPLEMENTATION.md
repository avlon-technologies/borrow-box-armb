#### `::BorrowBox.Lending.ItemListing.HiddenItemsKeepCommitments` — Requirement

#### `::BorrowBox.Lending.LendingCircles.CircleOnlyItemsReachOnlyMembers` — Requirement

> An item offered only to circles is shown to, and can be requested by, only people who at that moment share one of its circles with its owner.

#### `::BorrowBox.Lending.LendingCircles.CirclesGrowByInvitation` — Requirement

> Any member may start a circle and becomes its organiser; people join only by accepting an invitation from a current member; only the organiser removes members, and the organiser always stays a member.

#### `::BorrowBox.Lending.LendingCircles.MembershipChangesKeepCommitments` — Requirement

> Leaving, removal, or narrowing an item's audience refuses new circle-only requests from then on, but every reservation already made, pending or committed, continues through decision, handoff, extension and return unchanged.

#### `::BorrowBox.Lending.LendingCircles.OwnersChooseAudience` — Requirement

> Only an item's owner decides whether it is offered to everybody or only to chosen circles, and only circles the owner currently belongs to can be chosen.

#### `::BorrowBox.Lending.LoanCustody.HandoffIsAttributed` — Requirement

> The owner marks the item ready, the borrower confirms pickup and starts the return, and the owner confirms it is back; every step is recorded with who did it and when. (A06)

#### `::BorrowBox.Lending.LoanCustody.LateLoansRemainReturnable` — Requirement

> A loan past its due date is shown as overdue to both people and can still be returned normally. (A09)

#### `::BorrowBox.Lending.ReservationCoordination.ApprovalsNeverOverlap` — Requirement

> Overlapping pending requests may coexist, but no two committed reservations for one item ever overlap, even when approvals are submitted concurrently. (A04)

#### `::BorrowBox.Lending.ReservationCoordination.DecisionsFollowLifecycle` — Requirement

> Only a pending request may be approved or declined, only by the item's owner; only its borrower may cancel it; any other transition is refused. (A03)

#### `::BorrowBox.Lending.ReservationCoordination.ExtensionsRecheckConflicts` — Requirement

> A borrower may propose a later due date; only the owner may accept it, and acceptance re-checks the extended days against every other commitment. (A08)

#### `::BorrowBox.Lending.ReservationCoordination.NoSelfBorrowing` — Requirement

> No one may request to borrow an item they own. (A05)

#### `::BorrowBox.Lending.ReservationCoordination.RequestsPersistAsPending` — Requirement

> A borrower requests an inclusive date range with an optional note, and the request is durably pending until the owner decides or the borrower cancels. (A02)

#### `::BorrowBox.RepeatedSubmissionIsHarmless` — Requirement

> Submitting the same action twice (double click, retry, refresh) produces one effect, never a duplicate request, evidence entry or transition.

#### `::BorrowBox.StateSurvivesRestart` — Requirement

> Items, reservations, loans, evidence and history persist durably across restarts, and the demo seed is repeatable. (A11)

### BusinessRules (14)

#### `::BorrowBox.Lending.Library.CircleOnlyNeedsSharedCircle` — BusinessRule

- statement = A request for an item offered only to circles is refused unless, at the moment it is recorded, the requester and the owner are both active members of a circle the item is shared with. Items offered to everybody need no circle.

#### `::BorrowBox.Lending.Library.CommittedReservationsNeverOverlap` — BusinessRule

- statement = A request may be approved only if its inclusive range overlaps no other approved, ready, borrowed or returning reservation of the same item; the check and the commit are one atomic act.

#### `::BorrowBox.Lending.Library.EvidenceIsAppendOnly` — BusinessRule

- statement = Condition evidence is only ever added; an owner who disagrees with the borrower's account records their own evidence marked as a disagreement, and both remain.

#### `::BorrowBox.Lending.Library.ExtensionRecheck` — BusinessRule

- statement = An extension may be accepted only while the loan is open and only if the days between the current and proposed due date overlap no other commitment for the item.

#### `::BorrowBox.Lending.Library.HiddenItemsTakeNoNewRequests` — BusinessRule

- statement = A request to borrow a hidden item is refused; hiding changes nothing about requests and loans already made.

#### `::BorrowBox.Lending.Library.LoanStepsInOrder` — BusinessRule

- statement = Ready follows approval, pickup follows ready, return starts only while borrowed, and confirmation follows the start of return.

#### `::BorrowBox.Lending.Library.MembershipChangesKeepCommitments` — BusinessRule

- statement = Leaving, removal and narrowing an item's audience only refuse new circle-only requests; no reservation already made is cancelled, declined or blocked from its next step, and its people keep seeing the item.

#### `::BorrowBox.Lending.Library.NoSelfBorrowing` — BusinessRule

- statement = A request to borrow is refused when the requester owns the item.

#### `::BorrowBox.Lending.Library.OnlyMembersInvite` — BusinessRule

- statement = Only an active member may invite, and only someone not already invited or active in that circle; only the invited person accepts or declines.

#### `::BorrowBox.Lending.Library.OnlyPendingIsDecided` — BusinessRule

- statement = Approve and decline apply only to a pending request; cancel applies to the borrower's own request before pickup.

#### `::BorrowBox.Lending.Library.OrganiserStaysMember` — BusinessRule

- statement = The organiser removes members and can be neither removed nor leave.

#### `::BorrowBox.Lending.Library.OverdueIsInformational` — BusinessRule

- statement = A loan whose due date is before today in the community time zone is overdue; being overdue blocks nothing about returning it.

#### `::BorrowBox.Lending.Library.RequestsFitTheCalendar` — BusinessRule

- statement = A requested range starts no earlier than today in the community time zone, ends on or after its start, and is no longer than the item's maximum loan length.

#### `::BorrowBox.Lending.Library.ShareOnlyWhereMember` — BusinessRule

- statement = An owner can share an item only with circles they are an active member of; an item offered only to circles is reachable through a circle only while its owner is still an active member there.

### Derived behavioural traces

The traces in `acceptance/traces/` are the compiler's DERIVED process graph from the scenario's starting message: every hop classified as the model declares it (`reactive` / `correlated` where a Reaction or a Workflow establishes the consequence; `causal relation undeclared` where only topology connects them). A trace is architectural knowledge, not a runtime claim: it does not say what happens concurrently, how long anything takes, or that any event occurs. Where a scenario also carries an authored `expectedTrace`, that is the scenario author's expectation and is labelled as such.

### The behavioural projection — `BEHAVIOUR.md`

`BEHAVIOUR.md` is the same knowledge drawn for a reader: from each scenario's starting message, the trace as a tree, every Workflow it passes through expanded into its steps with the static order relation the definition establishes (which steps a transition path orders, which it leaves UNORDERED — potentially concurrent, statically, WORKFLOW-SEMANTICS §9.7 C4 — and where joins, exclusive decisions and waits synchronize), and the underspecified-causality findings: 0 along these traces. Every line says whether it is DECLARED, DERIVED or UNSPECIFIED. "Unordered" is the model's silence about order, never a scheduling claim: you choose whether unordered steps run concurrently, and you record the choice as an implementation policy, not as architecture. Each finding is a decision you would otherwise make silently — declare it (a Reaction, a correlation, a sink) or record it as a gap.

## 6. Semantic gaps — when the architecture is silent

If implementing requires a behaviour, message, store, consumer, ordering or rule the model does not declare:

1. **Do not invent it silently.** An undeclared claim implemented anyway is the defect this package exists to prevent.
2. Record the gap as `gaps/<yyyy-mm-dd>-<slug>.md` in the implementation repository: the one precise fact the architecture cannot currently express or does not declare; the evidence (which scenario, which element); the smallest change that would close it; and what the implementation does meanwhile (nothing, a feature flag, a fake).
3. Request an architecture change: a `.adl-change` whose `base` pins this package's state —

```
base package avlon.borrowbox version "cycle-1" state "sha256:2a970ccbcbf7166fcfbbd5a243cad584c7b1a07b646beba57defa39643be61a7"
```

4. When the change is accepted, the next package is built from the applied state (`node tools/development-package.mjs build … ` with `semantic.change`), and `node tools/development-package.mjs check <package> --change <file>` proves `package.changeState == change.base.state` before any work continues.
